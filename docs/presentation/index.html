Konflux / BYOB

PoC snapshot · ae92025

The BYOB PoC implements a shortcut for introducing new artifact types in Konflux. Developers provide an executable build script and select a builder image through the Pipeline. The platform keeps control of the trusted Task that executes that logic.

The default build-cmd is ["./build.sh"]. build-args appends argv entries without shell parsing. The script runs from the restored source checkout and must write at least one regular file to BUILD_OUTPUT. Trusted platform code validates and exports those outputs.

This deck describes published commit ae920259cdb87f111e12f2a10e9e01c01896b874. The current demonstration policy approves one pinned builder image; the broader design permits users to select images under the platform's approval policy.

The design change

Konflux retains the execution boundary

Previously, introducing a build step meant providing its logic in a trusted catalog Task. The Task encoded how to build the artifact, so a new tool or format often required catalog work and review.

BYOB separates the build logic from its execution envelope. The developer supplies the script and builder image. Konflux supplies run-build or run-build-remote, including the fixed runtime confinement, trusted restore/export steps, and provenance integration.

The script belongs to the source cloned for the build. The selected image provides the runtime and tools. Platform review remains necessary for the trusted execution Task, while source review can cover application build logic. The current PoC policy has a single approved builder image, so accepting another image still requires updating that policy.

User logic, trusted execution

PoC parameters: image, build-cmd, build-args

The default executable is ./build.sh, resolved in /var/source. build-cmd and build-args are arrays passed directly as command and arguments. The builder image must contain the executable's runtime. The script comes from the cloned source, rather than being supplied as an inline Tekton Task step.

The Rego command rule checks relative source paths without parent traversal and matches the attested command to a recorded step entryPoint and approved image digest. The builder rule compares the declared image with the policy's approved digest.

The fixed Task runs the developer step as UID 1000 with no privilege escalation and dropped capabilities. Trusted steps handle source restoration, registry authentication and output export. The developer step does not mount the registry or Git credential volumes. The service-account example disables token automount. Remote execution uses rootless Podman and keeps the SSH credential in trusted orchestration.

These checks support the intended confinement contract. The current Rego policy is not a full immutable-digest verification of all build Task content: it uses cluster Task names for run-build, run-build-remote and pack. Trusted Task identity and safe execution overrides must also be enforced by the platform. Source-path checks establish the recorded contract; protected Task definitions and runtime confinement provide the execution guarantee.

Multiple build Tasks

Chained and platform-matrix builds share this contract

A Pipeline can contain multiple run-build or run-build-remote Tasks. Conforma accepts a SOURCE_ARTIFACT input only when it matches the checkout artifact or a BUILD_ARTIFACT from a build Task in the same attestation. Additional BUILD_ARTIFACTS entries must match build results from that same attestation. Foreign inputs are rejected.

The diagram shows an example chain, not the only allowed topology. In the supplied byob-chained Pipeline, every build independently restores the original checkout. Build B receives Build A's output separately through BUILD_INPUTS/codegen/out/. The policy also permits a previous same-Pipeline build artifact as SOURCE_ARTIFACT.

This differs from the ADR's mutated-source handoff. The PoC exports only validated files written to BUILD_OUTPUT, without automatically forwarding source trees or caches. A chained build must copy any inputs it wants to preserve into its own BUILD_OUTPUT. pack collects selected build outputs into one OCI artifact. Matrix pipelines run builds per platform and preserve platform directories in the final payload.

Verification

The current PoC policy approves one builder image

The byob-pipeline-policy integration test calls ec validate image with the Chains public key. Signature and subject verification happen before the BYOB Rego policy evaluates the SLSA v0.2 PipelineRun statement. The policy result is returned through TEST_OUTPUT to the integration service.

The actual rules also require an approved Pipeline shape, checkout/build/pack Tasks, the pinned checkout bundle, source URL/commit consistency with Git material and checkout results, expected artifact type, and storage consistent with Pipeline parameters. The signature must describe the snapshot image being checked.

The rule set currently only approves the pinned Konflux task-runner image. It checks build/pack Task references by name, while immutable Task identity enforcement remains a platform integration obligation. Resource requests and limits may be overridden. Admission must prevent other execution overrides from replacing the reviewed plan or exposing credentials.

Conforma verifies signed evidence of the contract. Isolation is implemented by the trusted Task and platform; the Rego policy does not inspect a live cluster or independently prove VM allocation and teardown. Source VSA verification is not part of these current rules.

SLSA Build L3

Build L3 requires the trusted Tasks and platform isolation guarantees

The design allows new build logic without moving the trust boundary into that logic. Build L3's relevant guarantees come from isolated execution and unforgeable, accurate provenance. A trusted generic Task can run developer logic while preserving those guarantees, provided the platform enforces the execution boundary and Conforma verifies the resulting evidence.

The cluster must prevent build workloads from mutating TaskRun/PipelineRun status or reading signing keys, and disable token automount on build accounts. The Task separates developer execution from trusted credential-bearing steps. Remote builds require a fresh dedicated VM per TaskRun, destroyed after completion or cancellation. Controller localhost builds need equivalent isolation. Fixed runtime configuration and trusted Task identity must remain protected.

The PoC supports those deployment controls but does not establish them all by itself. The current policy checks recorded build evidence and input lineage; platform admission must additionally enforce immutable Task identities and reject unsafe execution overrides. Complete provenance capture, including remote image identity and matrix child builds, depends on the configured Chains deployment.

Build L3 does not require hermetic execution. Builds may fetch dependencies. The signed source identity and declared execution parameters still need to describe the actual build accurately. Source-track assurance is separate from Build L3.

Release integration

A Task in the release Pipeline invokes unpack-build-output in its first step to download and extract the artifacts built by BYOB. A later step in that same Task publishes the extracted files to the release destination. The use case determines the destination and the implementation of the publishing step.

Mount a shared volume or workspace in both steps so that the publishing step can read the extraction directory. The PoC supplies the reusable unpack StepAction; the release Task supplies the destination-specific publishing step.

pack publishes one OCI artifact per PipelineRun. Its artifact type is application/vnd.konflux.build-output.v1 and its only layer is payload.tar.gz, with media type application/vnd.oci.image.layer.v1.tar+gzip. The final manifest digest is the reference downstream consumers use.

A release Task can use the unpack-build-output StepAction to download and restore these files. Its image parameter is registry/repo@sha256:manifest-digest. Its destination parameter names an empty writable directory. The StepAction checks the artifact type, expected layer name/media type and downloaded layer digest, then validates and extracts the archive. Chained/task or matrix/platform directories remain in the payload.

Install the StepAction in the release Task's namespace or resolve its definition. The release Pipeline continues to reference its own Task, which invokes the StepAction. Registry authentication and trusted CA mounts belong to this trusted release-side consumer. It is not an additional developer-authored build Task or an entry in the BYOB build allowlist.
